# Models

All models are plain Java classes with no JPA or Hibernate annotations. They mirror the structure of their corresponding PostgreSQL table exactly. Foreign key relationships are represented as `Long` ID fields — never as nested objects. Fields that hold a `List` of another model are not database columns — they are populated in the Service layer via a second query. All models use Lombok `@Data`, `@Builder`, `@NoArgsConstructor`, and `@AllArgsConstructor`.

| Value | Meaning |
|---|---|
| `PENDING` | Order placed, awaiting processing |
| `PROCESSING` | Order confirmed and being prepared |
| `SHIPPED` | Order dispatched for delivery |
| `DELIVERED` | Order received by customer |

## `inventory/model/`

### `Inventory.java` → `inventory` table

| Field | Type | Notes |
|---|---|---|
| `id` | `Long` | Primary key |
| `productId` | `Long` | FK → `products(id)` ON DELETE CASCADE — NOT NULL UNIQUE (one-to-one with product) |
| `quantityAvailable` | `int` | Current stock level |

## Cross-Cutting Notes

**Why `boolean` fields are named without the `is` prefix in models:**
Lombok generates builder methods by dropping the `is` prefix from boolean field names. A field named `isBanned` gets a builder method `banned()` which is inconsistent and confusing. A field named `banned` gets `banned()` for the builder, `isBanned()` for the getter, and `setBanned()` for the setter — fully consistent. The same applies to `active`, `featured`, `defaultAddress`.

**Why foreign keys are always `Long` IDs and never nested objects:**
Each model mirrors exactly what one database table row contains. A `users` table row has a `role` VARCHAR column — not a nested `Role` object. A `cart_items` row has a `product_id` BIGINT column — not a nested `Product` object. Nested objects require JPA or manual joins. Since this project uses raw SQL and `JdbcTemplate`, nested object population is the responsibility of the Service layer, not the Model or RowMapper.

**Why `BigDecimal` is used for monetary fields:**
`double` and `float` use binary floating point which cannot represent most decimal fractions exactly. `0.1 + 0.2` in binary floating point does not equal `0.3`. For monetary calculations, even small rounding errors accumulate and produce incorrect totals. `BigDecimal` uses decimal arithmetic and is the correct Java type for money, prices, and financial calculations.

**Why snapshot fields exist in `OrderItem` and `Order`:**
If `OrderItem` stored only a `productId` foreign key, and the product was later renamed, repriced, or deleted, the historical order record would reflect the new name/price or break entirely. Snapshots freeze the data at the moment of purchase, making order history permanently accurate and immutable.
